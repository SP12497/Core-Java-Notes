# React Interview Notes — 4. React Context API

> Context is a React mechanism for making a value available to components deeper in the tree without manually passing it through every intermediate component.

---

# 1. What Problem Does Context Solve?

Consider:

```text
App
 └── ComponentA
      └── ComponentB
           └── ComponentC
                └── ComponentD
```

Suppose `App` owns:

```js
user
```

but only `ComponentD` needs it.

Without Context:

```text
App
 ↓ user
ComponentA
 ↓ user
ComponentB
 ↓ user
ComponentC
 ↓ user
ComponentD
```

The intermediate components receive `user` even though they don't need it.

This is commonly called **prop drilling**.

Context allows:

```text
App
 │
 │ Context Provider
 │
 ├── ComponentA
 │    └── ComponentB
 │         └── ComponentC
 │              └── ComponentD
 │                    ↓
 │                 useContext()
 │                    ↓
 │                  user
```

---

# 2. What Is Context?

Context provides a way to pass information through the React component tree without explicitly passing props at every level.

Typical use cases:

* Theme
* Current authenticated user
* Locale/language
* Application configuration
* Feature flags
* Other broadly shared values

Context is **not automatically a global state-management solution**.

---

# 3. Creating a Context

Use `createContext()`:

```jsx
import { createContext } from "react";

const UserContext = createContext(null);

export default UserContext;
```

The argument is the context's default value.

---

# 4. Providing Context

A provider makes a value available to descendants.

Traditional syntax:

```jsx
<UserContext.Provider value={user}>
  <App />
</UserContext.Provider>
```

Example:

```jsx
function App() {
  const user = {
    name: "Sagar"
  };

  return (
    <UserContext.Provider value={user}>
      <Dashboard />
    </UserContext.Provider>
  );
}
```

Now components below `Dashboard` can read the context.

---

# 5. Consuming Context with `useContext`

```jsx
import {
  useContext
} from "react";

function Profile() {
  const user =
    useContext(UserContext);

  return (
    <h1>
      Welcome {user.name}
    </h1>
  );
}
```

The component does not need:

```jsx
<Dashboard user={user}>
```

or:

```jsx
<Profile user={user}>
```

just to pass the value through.

---

# 6. React 19 Provider Syntax

React 19 supports rendering a context object directly as a provider:

```jsx
<UserContext value={user}>
  <Dashboard />
</UserContext>
```

Older/common syntax:

```jsx
<UserContext.Provider value={user}>
  <Dashboard />
</UserContext.Provider>
```

Both patterns may appear in existing codebases.

For interviews, know both.

---

# 7. Context Default Value

Example:

```jsx
const ThemeContext =
  createContext("light");
```

If a component calls:

```jsx
const theme =
  useContext(ThemeContext);
```

and there is no matching provider above it, the value is:

```text
"light"
```

The default value is **not** a fallback that changes dynamically.

It is the value returned when no matching provider exists above the component.

---

# 8. Context Does Not "Store" State by Itself

This is a common interview misconception.

Context:

```jsx
const UserContext =
  createContext(null);
```

does not itself create mutable application state.

You can combine Context with state:

```jsx
function UserProvider({
  children
}) {
  const [
    user,
    setUser
  ] = useState(null);

  return (
    <UserContext.Provider
      value={{
        user,
        setUser
      }}
    >
      {children}
    </UserContext.Provider>
  );
}
```

Here:

```text
useState
→ owns the state

Context
→ distributes access to that state
```


# 11. Custom Context Hook

A common pattern is to create a custom Hook:

```jsx
function useUser() {
  return useContext(UserContext);
}
```

Then components use:

```jsx
const {
  user,
  setUser
} = useUser();
```

instead of:

```jsx
const {
  user,
  setUser
} = useContext(UserContext);
```

---

# 12. Better Custom Hook with Error Checking

A robust pattern:

```jsx
import {
  createContext,
  useContext
} from "react";

const UserContext =
  createContext(null);

function useUser() {
  const context =
    useContext(UserContext);

  if (context === null) {
    throw new Error(
      "useUser must be used inside UserProvider"
    );
  }

  return context;
}

export {
  UserContext,
  useUser
};
```

This catches incorrect usage early.

# 13. Complete User Context Example

## `UserContext.jsx`

```jsx
import {
  createContext,
  useContext,
  useState
} from "react";

const UserContext =
  createContext(null);

function UserProvider({
  children
}) {
  const [
    user,
    setUser
  ] = useState(null);

  function login(userData) {
    setUser(userData);
  }

  function logout() {
    setUser(null);
  }

  return (
    <UserContext.Provider
      value={{
        user,
        login,
        logout
      }}
    >
      {children}
    </UserContext.Provider>
  );
}

function useUser() {
  const context =
    useContext(UserContext);

  if (context === null) {
    throw new Error(
      "useUser must be used inside UserProvider"
    );
  }

  return context;
}

export {
  UserProvider,
  useUser
};
```

# 14. Login Component

```jsx
import {
  useState
} from "react";

import {
  useUser
} from "./UserContext";

function Login() {
  const [
    username,
    setUsername
  ] = useState("");

  const {
    login
  } = useUser();

  function handleSubmit(event) {
    event.preventDefault();

    if (!username.trim()) {
      return;
    }

    login({
      id: 1,
      username
    });

    setUsername("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={username}
        onChange={event =>
          setUsername(
            event.target.value
          )
        }
        placeholder="Username"
      />

      <button type="submit">
        Login
      </button>
    </form>
  );
}

export default Login;
```

# 18. Context Re-render Behavior

This is one of the most important interview topics.

Suppose:

```jsx
<UserContext.Provider
  value={{
    user,
    login
  }}
>
```

A component consuming `UserContext` can re-render when the provider's context value changes.

The important comparison is the **identity of the provided value**.

---

# 19. Object Value and Re-renders

Consider:

```jsx
function UserProvider({
  children
}) {
  const [
    user,
    setUser
  ] = useState(null);

  return (
    <UserContext.Provider
      value={{
        user,
        setUser
      }}
    >
      {children}
    </UserContext.Provider>
  );
}
```

The object:

```jsx
{
  user,
  setUser
}
```

is newly created on each render.

Therefore its identity can change even when the underlying `user` value has not changed.

This can cause consumers to re-render.

---

# 20. Memoizing Context Value

For a performance-sensitive context:

```jsx
import {
  useCallback,
  useMemo,
  useState
} from "react";

function UserProvider({
  children
}) {
  const [
    user,
    setUser
  ] = useState(null);

  const login =
    useCallback(userData => {
      setUser(userData);
    }, []);

  const logout =
    useCallback(() => {
      setUser(null);
    }, []);

  const value =
    useMemo(
      () => ({
        user,
        login,
        logout
      }),
      [
        user,
        login,
        logout
      ]
    );

  return (
    <UserContext.Provider
      value={value}
    >
      {children}
    </UserContext.Provider>
  );
}
```

Do not blindly add `useMemo` and `useCallback` everywhere. Optimize when there is an actual reason.

---

# 21. Context Re-render Rule

A useful interview answer:

> When a provider's context value changes, components consuming that context are notified and may re-render. Passing a new object as the context value on every provider render can therefore cause unnecessary consumer updates.

---

# 22. Context and `React.memo`

A common misconception:

> "`React.memo` prevents a component using Context from re-rendering."

Not necessarily.

If a component consumes context:

```jsx
const theme =
  useContext(ThemeContext);
```

and the context value changes, the consumer can update even if the component is memoized.

`React.memo` primarily compares props.

Context is a separate source of updates.

---

# 23. Splitting Contexts

Avoid putting unrelated application data into one huge Context.

Bad:

```text
AppContext
├── user
├── theme
├── cart
├── notifications
├── language
├── settings
└── permissions
```

A change to one value can affect many consumers.

Prefer separate concerns when appropriate:

```text
UserContext
ThemeContext
CartContext
NotificationContext
```

This can improve organization and reduce unnecessary updates.

---

# 24. Context Selector Problem

React's built-in `useContext` does not provide arbitrary field-level subscriptions.

Suppose:

```jsx
const value = {
  user,
  theme,
  notifications
};
```

A consumer reading only:

```jsx
const {
  user
} = useContext(AppContext);
```

is still consuming the context as a whole.

Changing another part of the context value can still cause the consumer to update.

For very large/high-frequency shared state, an external state-management solution or selector-based approach may be more appropriate.

# 25. Context vs Props

### Props

```text
Parent
  ↓
Child
  ↓
Grandchild
```

Explicit data flow.

### Context

```text
Provider
   │
   ├── Component A
   ├── Component B
   └── Component C
          ↓
       useContext()
```

Useful when many descendants need the same value.

---

# 26. Context vs Redux

Context and Redux solve related but different problems.

### Context

Primarily provides values through the component tree.

```text
Provider
   ↓
Consumers
```

### Redux

Provides a structured external state store with:

* Centralized state
* Actions
* Reducers
* Middleware
* DevTools
* Selectors
* Predictable state transitions

Context can be part of a state-management solution, but Context itself is not equivalent to Redux.

Redux/Redux Toolkit is covered in a separate notes file.

---

# 27. Context vs Local State

Use local state when:

```text
Only one component needs the data.
```

Example:

```jsx
const [
  isOpen,
  setIsOpen
] = useState(false);
```

Use Context when:

```text
Many components at different levels need the same value.
```

Example:

```text
Theme
Current user
Locale
```

---

# 28. Context Is Not Always Better Than Props

Don't use Context simply to avoid writing one prop.

Props are often better when:

* Only a few components need the data.
* The relationship is explicit.
* The data is naturally parent → child.
* You want easier component reuse/testing.

Context is useful when prop drilling becomes a genuine architectural problem.

---

# 29. Context Provider Placement

The provider should be placed around the smallest part of the tree that needs the context.

Instead of:

```jsx
<Root>
  <UserProvider>
    <EntireApplication />
  </UserProvider>
</Root>
```

if only one feature needs it, consider:

```jsx
<Root>
  <Header />

  <FeatureProvider>
    <Feature />
  </FeatureProvider>

  <Footer />
</Root>
```

This keeps the context scope smaller.

---

# 30. Nested Providers

Providers can be nested.

```jsx
<ThemeProvider>
  <UserProvider>
    <CartProvider>
      <App />
    </CartProvider>
  </UserProvider>
</ThemeProvider>
```

Each provider manages its own context.

---

# 31. Multiple Instances of the Same Context

You can have multiple providers for the same context.

```jsx
<ThemeContext value="dark">
  <DarkSection />
</ThemeContext>

<ThemeContext value="light">
  <LightSection />
</ThemeContext>
```

A consumer reads the value from its nearest matching provider.

Conceptually:

```text
Root
 │
 ├── ThemeProvider("dark")
 │      └── Component A → dark
 │
 └── ThemeProvider("light")
        └── Component B → light
```

---

# 32. Nearest Provider Wins

Example:

```jsx
<ThemeContext value="light">
  <Page>
    <ThemeContext value="dark">
      <Button />
    </ThemeContext>
  </Page>
</ThemeContext>
```

`Button` receives:

```text
dark
```

because the inner provider is the nearest provider.

---

# 33. Context Outside Provider

Suppose:

```jsx
const ThemeContext =
  createContext("light");
```

and:

```jsx
function Button() {
  const theme =
    useContext(ThemeContext);

  return <button>{theme}</button>;
}
```

If `Button` isn't under a provider:

```text
theme = "light"
```

because `"light"` is the context default.

If the default is `null`:

```jsx
const UserContext =
  createContext(null);
```

then:

```text
user = null
```

outside a provider.

# 34. Theme Context Example

A common real-world Context use case is application theme.

```jsx
import {
  createContext,
  useContext,
  useEffect,
  useState
} from "react";

const ThemeContext =
  createContext(null);

function ThemeProvider({
  children
}) {
  const [
    theme,
    setTheme
  ] = useState("light");

  function enableDark() {
    setTheme("dark");
  }

  function enableLight() {
    setTheme("light");
  }

  useEffect(() => {
    document.documentElement.dataset.theme =
      theme;
  }, [theme]);

  return (
    <ThemeContext.Provider
      value={{
        theme,
        enableDark,
        enableLight
      }}
    >
      {children}
    </ThemeContext.Provider>
  );
}

function useTheme() {
  const context =
    useContext(ThemeContext);

  if (!context) {
    throw new Error(
      "useTheme must be used inside ThemeProvider"
    );
  }

  return context;
}

export {
  ThemeProvider,
  useTheme
};
```

# 36. Context + Reducer

Context can be combined with `useReducer`.

This is useful when shared state has complex transitions.

```jsx
import {
  createContext,
  useContext,
  useReducer
} from "react";

const TodoContext =
  createContext(null);

const initialState = {
  todos: []
};

function reducer(
  state,
  action
) {
  switch (action.type) {
    case "add":
      return {
        ...state,
        todos: [
          ...state.todos,
          action.payload
        ]
      };

    case "remove":
      return {
        ...state,
        todos: state.todos.filter(
          todo =>
            todo.id !==
            action.payload
        )
      };

    default:
      return state;
  }
}

function TodoProvider({
  children
}) {
  const [
    state,
    dispatch
  ] = useReducer(
    reducer,
    initialState
  );

  return (
    <TodoContext.Provider
      value={{
        state,
        dispatch
      }}
    >
      {children}
    </TodoContext.Provider>
  );
}

function useTodos() {
  const context =
    useContext(TodoContext);

  if (!context) {
    throw new Error(
      "useTodos must be used inside TodoProvider"
    );
  }

  return context;
}

export {
  TodoProvider,
  useTodos
};
```

This pattern is sometimes described as:

```text
Context + useReducer
```

It can provide centralized application state without Redux.

# 37. Context + Reducer Mental Model

```text
                 Provider
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
        state              dispatch
          │                   │
          │                   ↓
          │                action
          │                   │
          │                reducer
          │                   │
          └─────────────── new state
```

This is particularly useful when many components need to dispatch related state transitions.

# 38. Context Performance Considerations

Potential problem:

```jsx
<Context value={{
  state,
  setState,
  someFunction
}}>
```

If the provider re-renders and creates a new object/function every time, the context value identity may change.

Possible techniques:

### 1. Split contexts

```text
UserContext
ThemeContext
```

### 2. Memoize values where useful

```jsx
const value =
  useMemo(
    () => ({
      user,
      logout
    }),
    [user, logout]
  );
```

### 3. Keep provider state local to the smallest required subtree.

### 4. Use an external state library when application requirements justify it.

---

# 39. Context Does Not Automatically Persist Data

Context state disappears when the provider is unmounted or the page/application is reloaded.

For persistence, use an appropriate storage/backend strategy.

For example:

```text
Context
+
localStorage
```

or:

```text
Context
+
server/session
```

depending on the data.

Do not say:

> "Context stores data permanently."

It does not.

---

# 40. Context and Browser Storage

You can initialize state from storage:

```jsx
const [
  theme,
  setTheme
] = useState(() => {
  return (
    localStorage.getItem(
      "theme"
    ) ?? "light"
  );
});
```

Then synchronize:

```jsx
useEffect(() => {
  localStorage.setItem(
    "theme",
    theme
  );
}, [theme]);
```

Context can expose the state:

```jsx
<ThemeContext value={{
  theme,
  setTheme
}}>
```

Here:

```text
Context
→ distributes state

localStorage
→ persists state in the browser
```

They have different responsibilities.

# 41. Common Context Mistakes

## Mistake 1 — Context for everything

Do not create Context for every piece of state.

Local state:

```jsx
const [isOpen, setIsOpen] =
  useState(false);
```

is usually simpler when only one component needs it.

---

## Mistake 2 — Mutating context state

If context exposes:

```jsx
const {
  user,
  setUser
} = useUser();
```

don't mutate:

```jsx
// ❌
user.name = "Rahul";
```

Use:

```jsx
setUser(prev => ({
  ...prev,
  name: "Rahul"
}));
```

---

## Mistake 3 — Giant Context

Avoid:

```jsx
<AppContext
  value={{
    user,
    cart,
    theme,
    notifications,
    products,
    settings,
    ...
  }}
>
```

unless the architecture genuinely requires it.

Split by domain when appropriate.

---

## Mistake 4 — Missing Provider

This:

```jsx
function Profile() {
  const {
    user
  } = useUser();

  // ...
}
```

requires:

```jsx
<UserProvider>
  <Profile />
</UserProvider>
```

somewhere above it.

---

## Mistake 5 — Assuming Context is Redux

Context provides values through the React tree.

Redux provides an external state-management architecture.

They should not be treated as identical technologies.

# 43. Context vs `useState`

`useState` answers:

> Where is the state stored and updated?

Context answers:

> How can descendants access a value without passing it through every component?

Together:

```jsx
const [
  user,
  setUser
] = useState(null);

<UserContext value={{
  user,
  setUser
}}>
```

---

# 44. Context vs `useReducer`

`useReducer` answers:

> How should complex state transitions be organized?

Context answers:

> How should descendants access the state/dispatch?

Together:

```text
useReducer
    ↓
state + dispatch
    ↓
Context
    ↓
descendants
```

---

# 45. Context vs Redux

| Context                                          | Redux / Redux Toolkit                           |
| ------------------------------------------------ | ----------------------------------------------- |
| React built-in mechanism                         | External state-management library               |
| Distributes values through tree                  | External centralized store                      |
| Simple shared values                             | Complex application state                       |
| No built-in action/reducer architecture required | Actions/reducers are core concepts              |
| No built-in DevTools equivalent                  | Redux DevTools ecosystem                        |
| Re-render behavior tied to context consumers     | Selectors can subscribe to selected state       |
| Good for theme/auth/config/etc.                  | Useful for larger structured state requirements |

This does **not** mean Redux is always necessary for large applications or Context is always bad for them. Architecture depends on the application.

# 46. Context API Interview Questions

## What is Context API?

> Context provides a mechanism for passing values through a React component tree without explicitly passing props through every intermediate component.

---

## What problem does Context solve?

> It can reduce prop drilling when many descendants need access to the same value.

---

## Does Context replace Redux?

> Not directly. Context is a value-distribution mechanism. Redux provides a more complete external state-management architecture.

---

## Does Context store state?

> Context itself doesn't create state. It can distribute state created with `useState`, `useReducer`, or another source.

---

## What happens when Context value changes?

> Consumers of that context are notified and may re-render based on the changed context value.

---

## Can Context cause performance problems?

Yes.

For example:

```jsx
<Context value={{
  user,
  setUser
}}>
```

creates a new object when the provider renders.

Large contexts with frequently changing values can cause many consumers to update.

Possible solutions include:

* Splitting contexts
* Memoizing values when useful
* Keeping providers scoped
* Using an external store when appropriate

---

## What is prop drilling?

> Passing data through multiple intermediate components that do not actually need the data themselves.

---

## What is `useContext`?

> A Hook that reads the value from the nearest matching context provider.

---

## What happens without a provider?

> The consumer receives the default value passed to `createContext()`.

# 48. Complete Interview Example

```jsx
import {
  createContext,
  useContext,
  useMemo,
  useState
} from "react";

const AuthContext =
  createContext(null);

function AuthProvider({
  children
}) {
  const [
    user,
    setUser
  ] = useState(null);

  function login(username) {
    setUser({
      id: 1,
      username
    });
  }

  function logout() {
    setUser(null);
  }

  const value =
    useMemo(
      () => ({
        user,
        login,
        logout
      }),
      [user]
    );

  return (
    <AuthContext value={value}>
      {children}
    </AuthContext>
  );
}

function useAuth() {
  const context =
    useContext(AuthContext);

  if (context === null) {
    throw new Error(
      "useAuth must be used inside AuthProvider"
    );
  }

  return context;
}

function Login() {
  const {
    login
  } = useAuth();

  return (
    <button
      onClick={() =>
        login("Sagar")
      }
    >
      Login
    </button>
  );
}

function Profile() {
  const {
    user,
    logout
  } = useAuth();

  if (!user) {
    return (
      <p>
        Not logged in
      </p>
    );
  }

  return (
    <div>
      <p>
        Welcome {user.username}
      </p>

      <button onClick={logout}>
        Logout
      </button>
    </div>
  );
}

function App() {
  return (
    <AuthProvider>
      <Login />
      <Profile />
    </AuthProvider>
  );
}

export default App;
```

# 49. Final Mental Model

```text
                  Context
                     │
              createContext()
                     │
                     ↓
                  Provider
                     │
                value={...}
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
    Component A  Component B  Component C
                                  │
                                  ↓
                             useContext()
                                  │
                                  ↓
                                value
```

If the value comes from state:

```text
useState / useReducer
          ↓
       Provider
          ↓
       Context
          ↓
      Consumers
```

The most important interview sentence:

> **Context solves value propagation through the component tree; it does not by itself define how application state is stored, updated, persisted, or synchronized.**
