# 6. React Performance Optimization

React performance optimization is mainly about **avoiding unnecessary work** while keeping the application simple and maintainable.

The most important principle is:

> **Measure first, then optimize the actual bottleneck.**

Premature optimization can make React code harder to understand without providing a meaningful performance improvement.

---

# 1. What Causes a React Component to Re-render?

A component can re-render when:

1. Its state changes.
2. Its parent re-renders.
3. A context value it consumes changes.
4. A subscribed external store changes.
5. A hook causes an update.

Example:

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}
```

Calling:

```js
setCount(count + 1);
```

schedules a re-render.

---

# 2. Re-render Does Not Mean DOM Rebuild

A React re-render does **not** mean the entire browser DOM is recreated.

Conceptually:

```text
State update
     ↓
Component renders again
     ↓
React creates a new element tree
     ↓
Reconciliation
     ↓
Only necessary DOM changes
```

React compares the new result with the previous one and commits the necessary changes to the DOM.

Therefore:

> **Re-rendering a component is not the same thing as repainting the entire page.**

---

# 3. Reconciliation

Reconciliation is the process React uses to determine what changed between renders.

For example:

```jsx
return (
  <div>
    <h1>{name}</h1>
    <button>Save</button>
  </div>
);
```

If only `name` changes, React can update the relevant text without recreating the entire DOM subtree.

---

# 4. Keys and Performance

Keys help React identify list items.

```jsx
users.map((user) => (
  <UserCard
    key={user.id}
    user={user}
  />
));
```

Stable keys help React preserve component identity correctly.

Avoid using array indexes as keys when items can:

* Be reordered
* Be inserted
* Be deleted
* Be filtered

Bad:

```jsx
users.map((user, index) => (
  <UserCard
    key={index}
    user={user}
  />
));
```

Prefer:

```jsx
users.map((user) => (
  <UserCard
    key={user.id}
    user={user}
  />
));
```

Keys are primarily about **identity and reconciliation correctness**, not simply a performance trick.

---

# 5. `React.memo`

`React.memo` memoizes a component.

```jsx
const UserCard = React.memo(function UserCard({
  user,
}) {
  return <div>{user.name}</div>;
});
```

If the parent re-renders, React can skip rendering `UserCard` when its props are considered equal.

By default, React compares props using shallow/reference equality.

---

# 6. When `React.memo` Helps

Suppose:

```jsx
function App() {
  const [count, setCount] = useState(0);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <ExpensiveComponent />
    </>
  );
}
```

If `ExpensiveComponent` does expensive work and receives stable props, memoization may prevent unnecessary re-renders.

```jsx
const ExpensiveComponent = React.memo(
  function ExpensiveComponent() {
    return <div>Expensive UI</div>;
  }
);
```

---

# 7. When `React.memo` Doesn't Help

Consider:

```jsx
function App() {
  const user = {
    name: "John",
  };

  return <UserCard user={user} />;
}
```

Even if:

```jsx
const UserCard = React.memo(...);
```

the object is recreated on every render.

Therefore:

```js
previousUser !== nextUser
```

because they are different object references.

This can cause `UserCard` to render again.

---

# 8. `useMemo`

`useMemo` memoizes the result of a calculation.

```jsx
const filteredUsers = useMemo(() => {
  return users.filter((user) =>
    user.name
      .toLowerCase()
      .includes(search.toLowerCase())
  );
}, [users, search]);
```

The calculation is recomputed when:

```text
users
```

or:

```text
search
```

changes.

---

# 9. `useMemo` Is Not a Guarantee

`useMemo` should be treated as a **performance optimization**, not a semantic requirement.

Do not write:

```jsx
const name = useMemo(
  () => user.name,
  [user]
);
```

just because you can.

The calculation is trivial and memoization adds complexity.

Prefer:

```jsx
const name = user.name;
```

Use `useMemo` when the calculation is sufficiently expensive or when stable identity is useful for another optimization.

---

# 10. `useCallback`

`useCallback` memoizes a function reference.

```jsx
const handleDelete = useCallback(
  (id) => {
    setUsers((users) =>
      users.filter((user) => user.id !== id)
    );
  },
  []
);
```

The function reference remains stable between renders as long as its dependencies remain unchanged.

---

# 11. Why `useCallback` Can Matter

Consider:

```jsx
const UserList = React.memo(function UserList({
  users,
  onDelete,
}) {
  // ...
});
```

Parent:

```jsx
function App() {
  const [users, setUsers] = useState([]);

  const handleDelete = useCallback((id) => {
    setUsers((currentUsers) =>
      currentUsers.filter((user) => user.id !== id)
    );
  }, []);

  return (
    <UserList
      users={users}
      onDelete={handleDelete}
    />
  );
}
```

Without `useCallback`, a new function could be created on every render.

With `React.memo`, that new function reference could cause the child to re-render.

---

# 12. `useCallback` Does Not Automatically Make Code Faster

This:

```jsx
const handleClick = useCallback(() => {
  console.log("clicked");
}, []);
```

is not automatically better than:

```jsx
const handleClick = () => {
  console.log("clicked");
};
```

`useCallback` itself has some overhead and adds dependency-management complexity.

Use it when stable function identity provides a meaningful benefit.

---

# 13. `useMemo` vs `useCallback`

| Hook          | Memoizes             |
| ------------- | -------------------- |
| `useMemo`     | A calculated value   |
| `useCallback` | A function reference |

Example:

```jsx
const total = useMemo(
  () => calculateTotal(items),
  [items]
);
```

versus:

```jsx
const handleSubmit = useCallback(
  () => submitForm(data),
  [data]
);
```

A useful mental shortcut:

```text
useMemo
→ remember a value

useCallback
→ remember a function
```

---

# 14. `React.memo` + `useCallback` + `useMemo`

These tools are often discussed together.

Example:

```jsx
const Child = React.memo(function Child({
  data,
  onSelect,
}) {
  return (
    <button onClick={onSelect}>
      {data.name}
    </button>
  );
});

function Parent() {
  const [count, setCount] = useState(0);

  const data = useMemo(
    () => ({
      name: "React",
    }),
    []
  );

  const onSelect = useCallback(() => {
    console.log("selected");
  }, []);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <Child
        data={data}
        onSelect={onSelect}
      />
    </>
  );
}
```

Now `Child` can skip rendering when `Parent` changes only because of `count`.

But this is useful only when the optimization actually matters.

---

# 15. React Compiler

Modern React tooling can automatically optimize some component and hook patterns through the **React Compiler**.

This reduces the need for manually adding memoization in applications configured to use the compiler.

However:

* `useMemo` still exists.
* `useCallback` still exists.
* `React.memo` still exists.
* Manual memoization can still be relevant in specific cases.
* You should understand what the compiler is optimizing rather than blindly adding memoization.

Interview answer:

> React Compiler can automatically optimize many patterns that previously required manual memoization, but `useMemo`, `useCallback`, and `React.memo` remain important concepts and APIs.

---

# 16. Context and Performance

Context can cause consumers to re-render when the provider's value changes.

Example:

```jsx
<AuthContext.Provider
  value={{
    user,
    login,
    logout,
  }}
>
  {children}
</AuthContext.Provider>
```

The object:

```js
{
  user,
  login,
  logout
}
```

can receive a new reference on every provider render.

You can sometimes stabilize it:

```jsx
const value = useMemo(
  () => ({
    user,
    login,
    logout,
  }),
  [user, login, logout]
);

return (
  <AuthContext.Provider value={value}>
    {children}
  </AuthContext.Provider>
);
```

But don't automatically memoize every context value.

---

# 17. Split Contexts

A large context can cause unrelated consumers to update together.

Instead of:

```text
AppContext
├── theme
├── user
├── notifications
├── cart
└── settings
```

consider separate contexts:

```text
ThemeContext
AuthContext
NotificationContext
CartContext
```

This can reduce unnecessary subscriptions and make responsibilities clearer.

---

# 18. State Colocation

One of the simplest React performance techniques is **keeping state as close as possible to where it is needed**.

Instead of:

```text
App
 ├── state for Modal
 ├── state for Search
 ├── state for Form
 └── state for Sidebar
```

move state down when it doesn't need to be shared.

Example:

```jsx
function SearchBox() {
  const [query, setQuery] = useState("");

  return (
    <input
      value={query}
      onChange={(event) =>
        setQuery(event.target.value)
      }
    />
  );
}
```

This prevents unrelated parts of the application from depending on that state.

---

# 19. Avoid Unnecessary Global State

Not every state value belongs in:

* Redux
* Context
* Zustand
* Another global store

For example:

```jsx
const [isModalOpen, setIsModalOpen] = useState(false);
```

is usually better than globalizing modal state unnecessarily.

A good rule:

> Start with local state. Lift or globalize it when there is a real sharing requirement.

---

# 20. Derived State

Avoid storing values that can be calculated from existing state.

Bad:

```jsx
const [items, setItems] = useState([]);
const [itemCount, setItemCount] = useState(0);
```

Now two pieces of state must stay synchronized.

Prefer:

```jsx
const [items, setItems] = useState([]);

const itemCount = items.length;
```

This creates a single source of truth.

---

# 21. Avoid Unnecessary Effects

This pattern is often unnecessary:

```jsx
const [fullName, setFullName] = useState("");

useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);
```

Instead:

```jsx
const fullName = `${firstName} ${lastName}`;
```

The effect introduces an additional render cycle and unnecessary state.

Remember:

> If something can be calculated during rendering from existing props/state, you often don't need an effect.

---

# 22. Large Lists

Rendering thousands of DOM elements can be expensive.

For very large lists, consider **virtualization**.

Instead of rendering:

```text
10,000 rows
```

render only the rows currently visible:

```text
Visible viewport
────────────────────
Row 101
Row 102
Row 103
Row 104
Row 105
────────────────────
```

Popular libraries include:

* `@tanstack/react-virtual`
* `react-window`

The core concept is called:

> **Windowing / virtualization**

---

# 23. Example of Virtualization Concept

Without virtualization:

```jsx
items.map((item) => (
  <Row
    key={item.id}
    item={item}
  />
));
```

If `items` contains 50,000 elements, a large amount of DOM can be created.

With virtualization, only the visible region and a small buffer are rendered.

This can significantly reduce:

* DOM nodes
* Layout work
* Rendering work
* Memory usage

---

# 24. Code Splitting

Code splitting allows the application to load JavaScript in smaller chunks instead of downloading everything immediately.

React provides:

```js
lazy()
```

and:

```jsx
Suspense
```

Example:

```jsx
import { lazy, Suspense } from "react";

const Settings = lazy(
  () => import("./Settings")
);

function App() {
  return (
    <Suspense fallback={<p>Loading...</p>}>
      <Settings />
    </Suspense>
  );
}
```

The `Settings` component can be loaded when needed.

---

# 25. Route-Based Code Splitting

A common optimization is loading pages only when users navigate to them.

Conceptually:

```text
Initial bundle
├── Home

Later
├── Dashboard chunk
├── Settings chunk
└── Reports chunk
```

This can reduce initial JavaScript download and execution.

React Router applications commonly combine routing with lazy-loaded route components.

---

# 26. Bundle Size

Large JavaScript bundles can increase:

* Download time
* Parse time
* Compilation time
* Execution time
* Memory usage

Potential optimizations include:

* Code splitting
* Lazy loading
* Removing unnecessary dependencies
* Choosing smaller libraries where appropriate
* Tree-shaking
* Analyzing production bundles

---

# 27. Tree Shaking

Tree shaking removes unused code from production bundles when the tooling can statically determine it is unused.

For example:

```js
import {
  formatDate,
} from "./utils";
```

If the module contains many exports but only `formatDate` is used, bundlers can often eliminate unused exports.

Tree shaking works best with modern ES modules and appropriate build tooling.

---

# 28. Debouncing

Debouncing is useful when an event can fire very frequently.

Example:

```text
User types:

R
Re
Rea
Reac
React
```

Instead of making an API request for every keystroke, wait until the user stops typing.

Conceptually:

```text
Typing
  ↓
wait 300ms
  ↓
no new input?
  ↓
perform search
```

A debounce utility can be implemented or provided by a library.

---

# 29. Throttling

Throttling limits how frequently a function can run.

For example, a scroll event may fire many times per second.

Throttle:

```text
scroll event
scroll event
scroll event
     ↓
run handler
     ↓
wait
     ↓
run handler
```

### Difference

```text
Debounce
→ run after events stop

Throttle
→ run at most once per interval
```

---

# 30. Expensive Calculations

If rendering contains expensive calculations:

```jsx
const result = expensiveCalculation(data);
```

and the calculation is repeated unnecessarily, consider:

```jsx
const result = useMemo(
  () => expensiveCalculation(data),
  [data]
);
```

But first verify that the calculation is actually expensive enough to justify memoization.

---

# 31. Avoid Creating Huge Objects During Render

This:

```jsx
const config = {
  theme: "dark",
  language: "en",
  mode: "compact",
};
```

creates a new object on every render.

Usually this is completely fine.

It matters when `config` is passed to memoized children or used as a dependency where object identity affects behavior.

In those cases, restructure the component or stabilize the value when justified.

---

# 32. Avoid Inline Objects When Identity Matters

Potential issue:

```jsx
<Child
  options={{
    color: "red",
  }}
/>
```

Every parent render creates a new object.

If `Child` is memoized:

```jsx
const Child = React.memo(ChildComponent);
```

the new object can invalidate shallow prop comparison.

Possible solution:

```jsx
const options = useMemo(
  () => ({
    color: "red",
  }),
  []
);

return <Child options={options} />;
```

But again, don't add this optimization unless object identity is actually affecting performance.

---

# 33. Avoid Inline Functions When Identity Matters

Potential issue:

```jsx
<Child
  onClick={() => handleClick(id)}
/>
```

A new function is created on each render.

If the child is memoized and the callback identity matters, consider:

```jsx
const handleChildClick = useCallback(
  () => handleClick(id),
  [handleClick, id]
);
```

Then:

```jsx
<Child onClick={handleChildClick} />
```

However, inline functions themselves are **not inherently a performance problem**.

---

# 34. `useRef` for Mutable Values

`useRef` can hold a mutable value without causing a re-render when the value changes.

```jsx
const renderCount = useRef(0);

renderCount.current += 1;
```

Updating:

```js
renderCount.current
```

does not schedule a React render.

Useful examples include:

* DOM references
* Timer IDs
* Previous values
* Mutable instance-like values

Do not use refs as a replacement for state when the UI needs to update.

---

# 35. `useTransition`

`useTransition()` allows some updates to be marked as non-urgent.

```jsx
const [
  isPending,
  startTransition,
] = useTransition();
```

Example:

```jsx
function Search({ items }) {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState(items);

  const [isPending, startTransition] =
    useTransition();

  function handleChange(event) {
    const value = event.target.value;

    setQuery(value);

    startTransition(() => {
      setResults(
        items.filter((item) =>
          item.name
            .toLowerCase()
            .includes(value.toLowerCase())
        )
      );
    });
  }

  return (
    <>
      <input
        value={query}
        onChange={handleChange}
      />

      {isPending && <p>Updating results...</p>}

      {results.map((item) => (
        <div key={item.id}>
          {item.name}
        </div>
      ))}
    </>
  );
}
```

Important:

> `startTransition()` does not run JavaScript on another thread.

It tells React that the update is non-urgent and can be interrupted by more urgent work.

---

# 36. `useDeferredValue`

`useDeferredValue()` allows a value to have a deferred version.

```jsx
const deferredQuery =
  useDeferredValue(query);
```

Example:

```jsx
function SearchResults({ query }) {
  const deferredQuery =
    useDeferredValue(query);

  return (
    <Results query={deferredQuery} />
  );
}
```

The UI can keep the urgent input responsive while expensive rendering based on the deferred value happens at lower priority.

---

# 37. `useTransition` vs `useDeferredValue`

| `useTransition`               | `useDeferredValue`                            |
| ----------------------------- | --------------------------------------------- |
| Marks an update as non-urgent | Defers a value                                |
| You control the state update  | React gives you a deferred version            |
| Provides `isPending`          | Does not provide `isPending` directly         |
| Useful around update logic    | Useful when you receive/use an existing value |

Mental model:

```text
useTransition
→ "This state update can wait."

useDeferredValue
→ "This value can lag behind slightly."
```

# 38. Profiling

Before optimizing, measure the application.

React DevTools provides a **Profiler** that helps identify rendering performance problems.

Look for:

* Components rendering frequently
* Expensive render durations
* Unnecessary re-renders
* Slow interaction updates

A good workflow is:

```text
Problem
  ↓
Measure
  ↓
Identify bottleneck
  ↓
Optimize
  ↓
Measure again
```

# 39. Browser Performance Tools

For real-world performance debugging, React DevTools is only part of the toolkit.

Browser DevTools can help inspect:

* JavaScript execution
* Network requests
* Memory
* Layout
* Paint
* Long tasks
* Core Web Vitals

Performance optimization should consider the whole application, not just React rendering.

# 40. React Performance vs Web Performance

React rendering is only one part of application performance.

Overall performance can also depend on:

```text
Network
   +
Server
   +
JavaScript download
   +
JavaScript execution
   +
React rendering
   +
DOM/layout
   +
Images
   +
Fonts
```

Therefore, optimizing `useMemo()` won't fix a 10 MB JavaScript bundle or an API that takes five seconds to respond.

# 41. Common Performance Mistakes

### ❌ Memoizing everything

```jsx
const value = useMemo(...);
const callback = useCallback(...);
const Component = React.memo(...);
```

without measuring a problem.

### Better

Use memoization when it addresses a real rendering or identity problem.

---

### ❌ Using effects for derived values

```jsx
useEffect(() => {
  setTotal(price * quantity);
}, [price, quantity]);
```

Prefer:

```jsx
const total = price * quantity;
```

---

### ❌ Putting all state in global state

Global state can increase coupling and cause unnecessary updates.

---

### ❌ Rendering huge lists without virtualization

For very large datasets, consider virtualization.

---

### ❌ Loading every route immediately

Use route-level code splitting when appropriate.

---

### ❌ Assuming every re-render is bad

Re-renders are normal React behavior.

The goal is not:

> "Never re-render."

The goal is:

> "Avoid unnecessary expensive work."

# 42. Interview Questions

## Q: What is `React.memo()`?

> `React.memo` memoizes a component so React can skip rendering it when its props are considered equal.

---

## Q: What is `useMemo()`?

> `useMemo` memoizes the result of a calculation and recomputes it when its dependencies change.

---

## Q: What is `useCallback()`?

> `useCallback` memoizes a function reference and is useful when stable function identity matters.

---

## Q: Difference between `useMemo` and `useCallback`?

> `useMemo` memoizes a value; `useCallback` memoizes a function.

---

## Q: Does `React.memo` prevent all re-renders?

No.

A memoized component can still update because of:

* Its own state
* Context it consumes
* External store subscriptions
* Changed props

---

## Q: Does a parent re-render always mean all children update their DOM?

No.

React can render child components again while reconciliation determines that no DOM changes are required.

`React.memo` can additionally skip a child's render when its props are unchanged.

---

## Q: Is re-rendering always bad?

No.

Rendering is a normal part of React's programming model.

The concern is unnecessary **expensive** work.

---

## Q: Why should you avoid array indexes as keys?

Because indexes can represent different items after insertion, deletion, or reordering, causing incorrect component identity and state preservation.

---

## Q: What is code splitting?

> Code splitting divides application JavaScript into smaller chunks that can be loaded when needed.

---

## Q: What is lazy loading in React?

Using:

```js
lazy()
```

to dynamically load a component, typically combined with:

```jsx
<Suspense>
```

---

## Q: What is virtualization?

> Virtualization renders only the visible portion of a large collection instead of rendering every item into the DOM.

---

## Q: Difference between debounce and throttle?

> Debounce waits until events stop before running; throttle limits execution to at most a specified frequency.

---

## Q: How do you optimize a slow React application?

A strong interview answer:

> First I would profile the application and identify the actual bottleneck. Depending on the cause, I might optimize component boundaries, state placement, expensive calculations, memoization, large lists, code splitting, network requests, or bundle size. I would then measure again to verify the improvement.

---

```text
□ Profile before optimizing

□ Avoid unnecessary global state
□ Avoid unnecessary effects

□ Use stable keys

□ Use useMemo for expensive calculations
□ Use useCallback when function identity matters
□ Split large contexts when appropriate
□ Virtualize very large lists

□ Code-split the application
□ Optimize images and fonts
□ Reduce unnecessary dependencies

```
